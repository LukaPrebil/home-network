# Luba automations reference device-level entities only; job state is reconstructed from progress-reset and fresh-fault signals

Status: accepted (2026-07-31)

On 2026-07-30 the Mammotion-HA integration deleted `sensor.vrt_luba_task_area_path` at the moment a mowing job ended, killing the trigger backbone of three notification automations. The sensor looked like a stable device-level task-status enum but was a map-derived entity: one per task area, generated from the mower's cloud map/task objects, with its display name bugged upstream to the generic "Task area path" (Mammotion-HA issue 700). Map-derived entities (area switches, saved-task buttons, task-area sensors) appear, rename, and disappear whenever maps, zones, or tasks change on the mower side (upstream issues 337, 604, 739) - the same churn already replaced `switch.vrt_luba_area_area_1` with `_area_2` and will happen again.

We decided that Luba automations and dashboards may reference device-level entities only, and job state is reconstructed from them: a job end is `sensor.vrt_luba_progress` resetting to 0; progress-before-reset >= 90 means finished (observed completions peak at 99, never 100); below 90 with a fresh fault (`sensor.vrt_luba_last_error_time` within 15 minutes) means aborted; below 90 without one is a deliberate cancel and stays silent. Rain-while-mowing conditions on `lawn_mower.vrt_luba` in mowing/returning. We stay on integration v0.6.3: the v0.6.4 beta train adds no job-status signal, only calmer availability, so the design is identical on both.

Considered and rejected: upgrading to v0.6.4-beta first (no design change gained, beta risk on a mowing-critical integration); a max-progress helper entity plus dock trigger (more machinery for a race the progress-reset trigger avoids by reading `trigger.from_state`); re-keying to whatever task sensor the integration recreates (repeats the failure on the next map churn, even though it would look simpler). Consequences: a deliberate cancel above 90% notifies as finished (harmless); rain during an in-yard pause is silent (the mower's own rain detection handles the physical response); if upstream ever ships a genuinely stable job-status sensor, a new ADR must supersede this one before anything re-keys to it.
