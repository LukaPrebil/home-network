# Rebuild EOL guests side-by-side at new VMIDs with a staged cutover

Status: accepted (2026-08-21).

Seven of ten hosts run Ubuntu 25.04 plucky, which reached end of life on 2026-01-17; its security archive last published on 2026-01-19. Nothing is broken today, because `archive.ubuntu.com` still serves the suite and `apt-get update` succeeds, so the exposure is unpatched CVEs accumulating rather than tooling failure. Docker Engine is frozen at 29.2.1 on the plucky Docker hosts as a knock-on. The repository has already declared the fix and never propagated it: `vars/lxc.yml` and `vars/cloudinit_template.yml` both name 26.04, the template is downloaded on n5p, and only the `dev` VM was ever rebuilt onto it.

We rebuild rather than upgrade in place. Reaching 26.04 from 25.04 means two `do-release-upgrade` hops staged through 25.10, which is itself past end of life, and the upgrader needs meta-release overrides to run off an EOL release at all. Rebuilding is also what the repository is shaped for: roles reconstruct services, data is meant to live outside the guest, and a rebuild proves both claims rather than assuming them.

Each guest is replaced side by side at a new VMID, keeping its hostname and IP. Proxmox 9.2 has no VMID rename for containers or VMs, so renumbering back into the 200-205 block afterwards would cost a full `pct clone` and a second cutover per guest; the block moves to 210-215 instead, with the containers VM going 101 to 111, and the roughly eleven references across `vars/lxc.yml`, `setup-immich-nfs.yml`, `provision-truenas.yml` and the docs are updated once. The predecessor is kept stopped rather than destroyed, because LXC and VM snapshots are structurally impossible on this node (raw disks on NFS storage) and the weekly snapshot cron had failed every one of its logged runs. A stopped predecessor is the only rollback this fleet has.

The replacement's services are converged only after the predecessor is stopped, not alongside it. Most of these services keep their state on NFS exports that survive a rebuild untouched, and that same property makes concurrency unsafe: two Paperless instances would run two Postgres processes against one data directory, and Uptime Kuma, PDS, OctoEverywhere and the Arr stack share files the same way. A blue-green flip would trade a bounded outage for a corruption risk on the exact state the rebuild is meant to preserve. Rollback never depended on running both at once, so the staged order costs little.

Immich is excluded and becomes its own project. Its role pins ROCm 7.2 through AMD's noble installer, and AMD publishes no resolute target before the ROCm 31.x line, so rebuilding it onto 26.04 couples in a ROCm major move. It also carries a machine-learning worker that has been crashing silently since May, leaving 38 GB of core dumps inside a container writable layer, and a pending Immich v2 to v3 major. Those are three problems wearing one hat and they do not belong in a fleet-wide OS change. Investigation during this decision established that the guest-side ROCm packages are consumed only by the role's `rocminfo` diagnostic, since the machine-learning container ships its own 21 GB ROCm tree and receives no host ROCm bind mount, so the coupling is looser than it first appeared.

Consequences: each guest takes a bounded outage spanning state copy, provision, converge and validation rather than an instant flip, from a few minutes for AdGuard to roughly an hour for the containers VM. Every stopped predecessor must have `onboot` cleared the moment it is stopped, because Ansible's drift correction loops over declared guests only and the boot-time autostart reconciler starts anything still flagged, which on the next power event would bring a predecessor up on an IP its replacement already holds. The predecessors are destroyed in one batch after the last guest has soaked for a week. VM 101's `usb0` Thread radio passthrough was never declared in `vars/vms.yml` and is codified as part of this work, since a rebuilt VM would otherwise come up silently without the radio.
